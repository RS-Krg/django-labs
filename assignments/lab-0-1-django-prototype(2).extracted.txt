[Title] Лабораторная работа №0.1: Прототип информационной системы на Django — учёт заявок ИТ-отдела
[Normal] Продолжительность: ~3–3,5 часа (2 семинара; что не успели на занятии, доделывается дома)
[Normal] Цель: довести учебное приложение helpdesk из лабораторной №0 до работающего прототипа информационной системы. Пользователи входят под своими учётными записями, сотрудники регистрируют заявки через формы на сайте, ИТ-отдел их обрабатывает, у каждой роли свои права, а основные сценарии проверяются автоматическими тестами.
[Normal] Что понадобится: проект helpdesk в том состоянии, в котором его оставила лабораторная №0: окружение venv с Django, приложение helpdesk, модель Ticket, admin panel, страница /tickets/. Доступ в интернет нужен только для подключения стилей Bootstrap; без него прототип тоже работает, просто выглядит проще.
[Normal] Все команды выполняются в папке проекта при активированном окружении ((venv) в начале строки). Как вернуться к проекту, описано в части 6 лабораторной №0. Команды одинаковы для Windows, Linux и macOS, кроме активации окружения.
[Heading 1] Часть 1. Теория (≈15 мин)
[Heading 2] 1.1 Что такое прототип и зачем он корпоративной ИС
[Normal] Прототип — это работающая версия системы, на которой видно главное: какие данные хранятся, кто и что с ними делает, как выглядит основной сценарий работы. Его показывают заказчику, чтобы до больших затрат проверить, правильно ли поняты требования. Ошибку в модели данных или в правах доступа дешевле всего найти на прототипе: исправить её в готовой системе с фронтендом на React, контейнерами и CI/CD будет в разы дороже.
[Normal] Django удобен для прототипов: модели, admin panel, формы, вход в систему и права доступа уже есть «из коробки». Работающий прототип собирается за один-два дня.
[Normal] Прототип не обязательно выбрасывают. Модели, права и тесты из этой лабы почти без изменений переживут переход на PostgreSQL и REST API. Заменятся в основном HTML-шаблоны: в блоке React интерфейс уйдёт во фронтенд.
[Heading 2] 1.2 Сценарий прототипа
[TABLE]
Роль | Что делает в системе
Сотрудник (любой работник университета) | входит в систему, регистрирует заявку, видит только свои заявки, может исправить заявку, пока её не взяли в работу
ИТ-специалист (группа «ИТ-отдел») | видит все заявки, ищет и фильтрует их, назначает исполнителя, меняет статус
Администратор | ведёт справочники (категории заявок) и учётные записи через admin panel
[/TABLE]
[Normal] Такая таблица и есть минимальное техническое задание для прототипа. Каждая строка превратится в код и в тест.
[Heading 2] 1.3 Формы и цикл GET/POST
[Normal] Работа с любой формой на сайте устроена одинаково:
[Normal] 1. GET — браузер просит страницу, сервер отдаёт пустую (или заполненную текущими данными) форму.
[Normal] 2. POST — пользователь нажал «Сохранить», браузер отправляет введённые данные.
[Normal] 3. Сервер проверяет данные (валидация). Если есть ошибки, он снова показывает ту же форму с введёнными значениями и сообщениями об ошибках.
[Normal] 4. Если всё верно, сервер сохраняет данные и отвечает перенаправлением (redirect) на другую страницу.
[Normal] Последний шаг называется Post/Redirect/Get. Без него после сохранения браузер остаётся на ответе POST-запроса, и нажатие F5 отправит форму повторно: появится дубль заявки.
[Normal] В Django для этого есть ModelForm: форма, которая строится по модели. Поля, их типы, обязательность и проверки длины Django берёт из модели, а сохранение выполняет одной командой form.save().
[Normal] Каждая POST-форма в Django должна содержать {% csrf_token %}. Это защита от CSRF-атаки: чужой сайт не сможет незаметно отправить форму от имени пользователя, который сейчас вошёл в нашу систему. Без токена Django отвечает ошибкой 403.
[Heading 2] 1.4 Аутентификация и авторизация
[List Bullet] Аутентификация — кто ты? Проверка логина и пароля, вход и выход.
[List Bullet] Авторизация — что тебе можно? Проверка прав на конкретное действие.
[Normal] Что для этого есть в Django:
[TABLE]
Механизм | Назначение
User | учётная запись: логин, пароль (хранится в виде хеша), ФИО, флаги is_staff и is_superuser
Permission | право на действие с моделью. Для каждой модели Django сам создаёт четыре права: add_, change_, delete_, view_
Group | группа пользователей с набором прав. Права выдают группе, а людей включают в группы
@login_required | view доступен только вошедшим, остальных перенаправляет на страницу входа
@permission_required | view доступен только пользователям с указанным правом
user.has_perm("app.codename") | проверка права в коде
[/TABLE]
[Normal] Стандартные права работают на уровне всей модели: «может изменять заявки». Правило «сотрудник видит только свои заявки» относится к конкретным записям, и встроенных прав для этого нет. Такие правила реализуют фильтрацией выборки: сотруднику просто не попадают в запрос чужие записи.

[Heading 1] Часть 3. Практика — расширяем модель данных (≈20 мин)
[Normal] Что делаем и зачем: модели из лабы №0 мало для реальной работы. Нужны категории (справочник), приоритет, подробное описание, а главное — связь заявки с пользователями: кто зарегистрировал и кто исполняет.
[Normal] 1. Заменить содержимое helpdesk/models.py:
[TABLE]

      LOW = "low", "Низкий" /         NORMAL = "normal", "Обычный" /         HIGH = "high", "Высокий" /  /     title = models.CharField("Тема", max_length=200) /     author = models.CharField("Кто models.ForeignKey( /         settings.AUTH_USER_MODEL, /         verbose_name="Зарегистрировал", /         on_delete=models.SET_NULL, /         null=True, /         blank=True, / [/TABLE]
[TABLE]
Элемент | Что означает
ForeignKey(Category, ...) | связь «многие к одному»: у заявки одна категория, у категории много заявок. В БД — столбец category_id
on_delete=models.PROTECT | нельзя удалить категорию, пока на неё ссылается хоть одна заявка
on_delete=models.SET_NULL | если удалить пользователя, заявки останутся, а ссылка на него обнулится. Требует null=True
null=True / blank=True | null — в БД разрешено пустое значение; blank — в формах поле можно не заполнять
settings.AUTH_USER_MODEL | ссылка на модель пользователя через настройку, а не напрямую на User. Если позже заменить модель пользователя на свою (как в лабе №3), эти связи менять не придётся
related_name="created_tickets" | имя обратной связи: user.created_tickets.all() — заявки, которые зарегистрировал пользователь. Две связи на одну модель обязаны иметь разные related_name, иначе makemigrations выдаст ошибку
auto_now=True | поле обновляется при каждом сохранении записи (в отличие от auto_now_add, которое заполняется один раз)
class Meta: verbose_name | название модели для людей: в admin panel будет «Заявки», а не «Tickets»
[/TABLE]
[Normal] Поле author («Кто обратился») оставляем: заявку могут принять по телефону, и тогда зарегистрировал её ИТ-специалист, а обратился другой человек.
[Normal] 2. Создать и применить миграцию:
[TABLE]
python manage.py makemigrations helpdesk / python manage.py migrate
[/TABLE]
[Normal] Все новые поля либо необязательные (null=True, blank=True), либо имеют значение по умолчанию, поэтому Django не задаёт вопросов: уже существующие заявки из лабы №0 получают пустую категорию, приоритет «Обычный» и т.д.
[Normal] 3. Посмотреть SQL миграции:
[TABLE]
python manage.py sqlmigrate helpdesk 0002
[/TABLE]
[Normal] Номер 0002 проверьте по имени файла в helpdesk/migrations/. Обратите внимание: SQLite не умеет многие виды ALTER TABLE, поэтому Django для неё создаёт новую таблицу new__helpdesk_ticket, копирует туда данные и удаляет старую. В PostgreSQL та же миграция превратится в простые ALTER TABLE ... ADD COLUMN.

[Heading 1] Часть 4. Практика — страница заявки (≈15 мин)
[Normal] Что делаем и зачем: у каждой заявки появляется своя страница со всеми полями. На неё будут вести ссылки из списка, на неё же будем возвращаться после сохранения формы.
[Normal] 1. Добавить в модель Ticket (в конец класса, после __str__) метод, который возвращает адрес страницы заявки, и импорт reverse в начало файла:
[TABLE]
from django.urls import reverse
[/TABLE]
[TABLE]
def get_absolute_url(self): /     return reverse("ticket_detail", args=[self.pk])
[/TABLE]
[Normal] reverse — то же самое, что {% url %} в шаблонах, только в Python-коде: по имени маршрута и параметрам строит адрес /tickets/5/. Метод get_absolute_url — соглашение Django: его используют redirect(ticket), кнопка «Смотреть на сайте» в admin panel и наши шаблоны.
[Normal] 2. Обновить helpdesk/views.py:
[TABLE]
from django.http import HttpResponse / from django.shortcuts import get_object_or_404, render /  / from .models import Ticket /  /  / def hello(request): /     return HttpResponse("Привет! Это учёт заявок ИТ-отдела.") /  /  / def ticket_list(request): /     tickets = Ticket.objects.select_related("category", "assignee").order_by("-created_at") /     return render(request, "helpdesk/ticket_list.html", {"tickets": tickets}) /  /  / def ticket_detail(request, pk): /     ticket = get_object_or_404(Ticket, pk=pk) /     return render(request, "helpdesk/ticket_detail.html", {"ticket": ticket})
[/TABLE]
[Normal] get_object_or_404 ищет запись и, если её нет, отвечает страницей «404 Не найдено» вместо падения с ошибкой DoesNotExist.
[Normal] 3. Добавить маршрут в helpdesk/urls.py:
[TABLE]
path("tickets/<int:pk>/", views.ticket_detail, name="ticket_detail"),
[/TABLE]
[Normal] <int:pk> — конвертер пути: часть адреса должна быть целым числом, Django передаст её во view параметром pk. Адрес /tickets/abc/ даже не дойдёт до view, сразу будет 404.

[Normal] 1. Создать файл helpdesk/forms.py:
[TABLE]
from django import forms /  / from .models import Ticket /  /  / class BootstrapFormMixin: /     """Добавляет полям формы CSS-классы Bootstrap.""" /  /     def __init__(self, *args, **kwargs): /         super().__init__(*args, **kwargs) /         for field in self.fields.values(): /             if isinstance(field.widget, forms.Select): /                 field.widget.attrs["class"] = "form-select" /             else: /                 field.widget.attrs["class"] = "form-control" /  /  / class TicketForm(BootstrapFormMixin, forms.ModelForm): /     class Meta: /         model = Ticket /         fields = ["title", "author", "category", "priority", "description"] /         widgets = { /             "description": forms.Textarea(attrs={"rows": 5}), /         } /         help_texts = { /             "author": "ФИО или подразделение, от которого пришла заявка", /         } /  /     def __init__(self, *args, **kwargs): /         super().__init__(*args, **kwargs) /         self.fields["category"].empty_label = "— не выбрана —" /  /     def clean_title(self): /         title = self.cleaned_data["title"].strip() /         if len(title) < 5: /             raise forms.ValidationError("Сформулируйте тему хотя бы в 5 символов.") /         return title
[/TABLE]
[TABLE]
Элемент | Что означает
Meta.fields | какие поля модели попадут в форму. Поля status, created_by, assignee сотрудник заполнять не должен, поэтому их здесь нет. Перечислять поля явно безопаснее, чем fields = "__all__": новое поле модели не окажется в форме случайно
widgets | как поле выглядит в HTML. По умолчанию TextField и так даёт <textarea>, здесь мы только задаём высоту

empty_label | текст пустого варианта в выпадающем списке. В Django 6.1 он по умолчанию «- Select an option -» и на русский не переведён, поэтому задаём сами

[Heading 1] Часть 7. Практика — обработка заявки ИТ-отделом (≈20 мин)
[Normal] Что делаем и зачем: ИТ-специалист на странице заявки назначает исполнителя и меняет статус. Это действие доступно только группе «ИТ-отдел», а в исполнители можно выбрать только её участников.
[Normal] 1. Добавить в helpdesk/forms.py импорт и вторую форму:

[Heading 1] Часть 8. Практика — поиск и фильтр по статусу (≈10 мин)
[Normal] Что делаем и зачем: когда заявок десятки, ИТ-отделу нужно быстро найти нужную. Делаем поиск по тексту и фильтр по статусу через параметры адреса: /tickets/?q=принтер&status=new.
[Normal] 1. В helpdesk/views.py добавить импорт и заменить ticket_list:
[TABLE]
from django.db.models import Q
[/TABLE]
[TABLE]
@login_required / def ticket_list(request): /     tickets = visible_tickets(request.user).order_by("-created_at") /  /     status = request.GET.get("status", "") /     query = request.GET.get("q", "").strip() /     if status: /         tickets = tickets.filter(status=status) /     if query: /         tickets = tickets.filter( /             Q(title__icontains=query) /             | Q(author__icontains=query) /             | Q(description__icontains=query) /         ) /  /     context = { /         "tickets": tickets, /         "statuses": Ticket.Status.choices, /         "status": status, /         "query": query, /     } /     return render(request, "helpdesk/ticket_list.html", context)
[/TABLE]
[Normal] request.GET — параметры из адреса после ?. Обычный .filter() объединяет условия через И, а Q(...) | Q(...) позволяет записать ИЛИ: «тема или автор или описание содержит строку». Фильтры накладываются на выборку из visible_tickets, поэтому сотрудник и в поиске видит только свои заявки.
[Normal] 2. В ticket_list.html после блока с заголовком и кнопкой добавить форму:
[TABLE]
<form method="get" class="row g-2 mb-3"> /   <div class="col-md-6"> /     <input class="form-control" type="search" name="q" value="{{ query }}" /            placeholder="Поиск по теме, автору, описанию"> /   </div> /   <div class="col-md-4"> /     <select class="form-select" name="status"> /       <option value="">Все статусы</option> /       {% for value, label in statuses %} /         <option value="{{ value }}" {% if value == status %}selected{% endif %}>{{ label }}</option> /       {% endfor %} /     </select> /   </div> /   <div class="col-md-2"> /     <button class="btn btn-outline-secondary w-100" type="submit">Найти</button> /   </div> / </form>
[/TABLE]
[Normal] Поиск — это форма с method="get": она ничего не меняет в данных, а результат поиска можно сохранить в закладки или переслать коллеге ссылкой. Поэтому {% csrf_token %} здесь не нужен.
[Normal] 3. Эксперимент. Найти заявку про принтер запросами принтер, Принтер и ПРИНТЕР. В SQLite часть запросов ничего не найдёт: регистронезависимое сравнение LIKE в SQLite работает только для латиницы, а icontains на SQLite превращается именно в LIKE. В PostgreSQL (лабы №1–3) все три варианта сработают. Это хороший пример, почему прототип на SQLite нельзя считать окончательной проверкой: поведение базы данных в продакшене может отличаться.

[Heading 1] Часть 10. Частые проблемы
[TABLE]
Симптом | Причина и решение
NoReverseMatch: Reverse for 'ticket_create' not found | в шаблоне используется имя маршрута, которого ещё нет в urls.py, или в имени опечатка. Проверить name= в path(...)
NoReverseMatch ... with arguments '('',)' | в {% url 'ticket_update' ticket.pk %} переменная ticket пустая: в контекст шаблона не передан объект
TemplateSyntaxError: Invalid block tag ... 'endblock' или «extends must be first» | {% extends %} стоит не первой строкой шаблона, или блоки {% block %} не закрыты
«Ошибка доступа (403). Ошибка проверки CSRF» | в форме нет {% csrf_token %}, или браузер блокирует cookie для сайта
После нажатия «Сохранить» страница просто перезагружается, ошибок не видно | шаблон не выводит ошибки формы: проверить вывод field.errors и non_field_errors. Или у <form> не указан method="post"
TemplateDoesNotExist: registration/login.html | шаблон входа лежит не в helpdesk/templates/registration/
«Выйти» даёт 405 Method Not Allowed | выход сделан ссылкой (GET). В Django 5+ нужна форма с method="post" и {% csrf_token %}
Сотрудник не видит старые заявки из лабы №0 | так и должно быть: у них пустой created_by. Их видит ИТ-отдел и суперпользователь
ИТ-специалист видит только свои заявки, карточки обработки нет | пользователь не включён в группу ИТ-отдел или группе не выдано право Can change ticket
В списке исполнителей пусто | в группе ИТ-отдел нет пользователей, или группа названа иначе (пробел, другой дефис). Название должно совпадать с groups__name="ИТ-отдел" в форме
Поиск ПРИНТЕР не находит «принтер» | особенность SQLite (см. часть 8, п. 3). В PostgreSQL работает
makemigrations спрашивает «Please select a fix: 1) Provide a one-off default…» | добавлено обязательное поле без значения по умолчанию, а в таблице уже есть записи. Выбрать 2) Quit, добавить полю null=True или default=... и повторить
fields.E304: Reverse accessor ... clashes | две связи на User без разных related_name
Стили Bootstrap не применились | нет доступа к cdn.jsdelivr.net. Прототип работает и без стилей. Для работы офлайн можно скачать bootstrap.min.css в папку helpdesk/static/ и подключить через {% load static %}
