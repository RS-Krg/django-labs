[Title] Лабораторная работа №0.2: Интернет-магазин на Django — каталог товаров
[Normal] Продолжительность: ~3–3,5 часа (2 семинара; что не успели на занятии, доделывается дома)
[Normal] Цель: начать новый проект — интернет-магазин, который к концу лабораторной №0.3 станет полноценным: каталог, корзина, заказы, личный кабинет, панель менеджера. В этой работе собираем витрину: проект из нескольких приложений, своя модель пользователя с первого дня, категории и товары с фотографиями, статические и медиафайлы, команда заполнения каталога демонстрационными данными, поиск, сортировка, постраничный вывод и тесты.
[Normal] Что понадобится: Python 3.12 или новее, умение создавать виртуальное окружение (лабораторная №0), опыт работы с шаблонами, формами и входом в систему (лабораторная №0.1), Git, доступ в интернет для установки пакетов и подключения стилей Bootstrap.
[Normal] Все команды выполняются в папке проекта при активированном окружении ((venv) в начале строки). Команды одинаковы для Windows, Linux и macOS, кроме создания и активации окружения: для них см. часть 3 лабораторной №0.
[Heading 1] Часть 1. Теория (≈15 мин)
[Heading 2] 1.1 Интернет-магазин как информационная система
[Normal] Интернет-магазин — удобный учебный пример корпоративной ИС: в нём есть всё, что встречается в реальных системах. Несколько ролей пользователей, справочники, учёт остатков, документы (заказы) со своим жизненным циклом и операции, которые должны выполняться целиком или не выполняться вовсе.
[TABLE]
Роль | Что делает
Покупатель | смотрит каталог, ищет товары, кладёт их в корзину, оформляет заказ, видит историю своих заказов
Менеджер | ведёт товары и остатки, обрабатывает заказы: подтверждает, передаёт в доставку, отменяет
Администратор | управляет пользователями, правами и справочниками
[/TABLE]
[TABLE]
Лабораторная | Что появится в магазине
№0.2 (эта) | каталог: категории, товары, фото, поиск, сортировка, страницы, тесты
№0.3 | корзина, регистрация, оформление заказа со списанием остатков, личный кабинет, панель менеджера, тесты; итоговое самостоятельное задание
[/TABLE]
[Heading 2] 1.2 Проект из нескольких приложений
[Normal] В лабораторных №0 и №0.1 всё жило в одном приложении helpdesk. Магазин делим на приложения по предметным областям:
[TABLE]
Приложение | За что отвечает | Когда появится
accounts | пользователи, регистрация, вход | эта лаба (модель), №0.3 (регистрация)
catalog | категории и товары, витрина | эта лаба
cart | корзина покупателя | №0.3
orders | заказы и их обработка | №0.3
[/TABLE]
[Normal] Каждое приложение — отдельная папка со своими моделями, view, шаблонами и тестами. Так код проще читать, а приложение при необходимости можно перенести в другой проект.
[Normal] Когда приложений несколько, имена маршрутов могут совпасть: detail может быть и у товара, и у заказа. Поэтому у маршрутов приложения задают пространство имён (app_name = "catalog"), и в шаблонах пишут {% url 'catalog:product_detail' ... %}.
[Heading 2] 1.3 Статические и медиафайлы
[TABLE]
 | Статические файлы (static) | Медиафайлы (media)
Что это | CSS, JavaScript, иконки, картинки оформления | файлы, которые загрузили пользователи: фото товаров, документы
Кто создаёт | разработчик | пользователи и менеджеры через сайт
Хранятся в Git | да | нет, папку media/ добавляют в .gitignore
Настройки | STATIC_URL, STATICFILES_DIRS | MEDIA_URL, MEDIA_ROOT
Кто отдаёт при разработке | runserver сам | runserver, если подключить в urls.py (см. часть 2)
Кто отдаёт в продакшене | веб-сервер (nginx), не Django | веб-сервер или объектное хранилище (S3)
[/TABLE]
[Heading 2] 1.4 Своя модель пользователя — с первого дня
[Normal] В лабораторной №0.1 мы использовали стандартную модель User, а в лабораторной №3 видно, как тяжело заменить её в работающем проекте. Документация Django прямо рекомендует: в каждом новом проекте сразу создавать свою модель пользователя, даже если пока она ничем не отличается от стандартной. Тогда позже можно спокойно добавить в неё поля (телефон, дату рождения, адрес доставки), не пересоздавая базу. Делаем это до первой команды migrate.
[Heading 1] Часть 2. Практика — новый проект (≈25 мин)
[Normal] Что делаем и зачем: создаём проект shop с нуля, ставим Django и библиотеку для работы с изображениями, настраиваем язык, шаблоны, статику, медиафайлы и свою модель пользователя.
[Normal] 1. Создать папку проекта и виртуальное окружение (подробно — в части 3 лабораторной №0):
[TABLE]
ОС | Команды
Windows (PowerShell) | mkdir C:\dev\shop, cd C:\dev\shop, py -m venv venv, venv\Scripts\Activate.ps1
Linux / macOS | mkdir -p ~/dev/shop && cd ~/dev/shop, python3 -m venv venv, source venv/bin/activate
[/TABLE]
[Normal] 2. Установить Django и Pillow — библиотеку для работы с изображениями. Без неё Django не позволит использовать в моделях поле ImageField:
[TABLE]
python -m pip install --upgrade pip / python -m pip install django pillow / python -m pip freeze > requirements.txt
[/TABLE]
[Normal] 3. Создать проект и два первых приложения:
[TABLE]
django-admin startproject config . / python manage.py startapp accounts / python manage.py startapp catalog
[/TABLE]
[Normal] 4. Создать в корне проекта папки для общих шаблонов, статических и медиафайлов:
[TABLE]
ОС | Команда
Windows (PowerShell) | mkdir templates, static\css, static\img, media
Linux / macOS | mkdir -p templates static/css static/img media
[/TABLE]
[Normal] 5. Отредактировать config/settings.py. Свежий Django генерирует его с одинарными кавычками, новые строки можно писать с любыми: для Python это одно и то же.
[List Bullet] подключить приложения:
[TABLE]
INSTALLED_APPS = [ /     # ... стандартные приложения django.contrib ... /     "django.contrib.staticfiles", /     "accounts", /     "catalog", / ]
[/TABLE]
[List Bullet] в TEMPLATES указать папку общих шаблонов проекта:
[TABLE]
"DIRS": [BASE_DIR / "templates"],
[/TABLE]
[List Bullet] язык и часовой пояс:
[TABLE]
LANGUAGE_CODE = "ru-ru" / TIME_ZONE = "Asia/Novosibirsk"
[/TABLE]
[List Bullet] после строки STATIC_URL = ... добавить:
[TABLE]
STATICFILES_DIRS = [BASE_DIR / "static"] /  / MEDIA_URL = "media/" / MEDIA_ROOT = BASE_DIR / "media" /  / AUTH_USER_MODEL = "accounts.User"
[/TABLE]
[TABLE]
Настройка | Что означает
TEMPLATES["DIRS"] | где искать шаблоны, кроме папок templates/ внутри приложений. Сюда положим base.html, общий для всех приложений магазина
STATICFILES_DIRS | папки со статикой проекта (кроме папок static/ внутри приложений)
MEDIA_URL, MEDIA_ROOT | по какому адресу и в какой папке на диске хранятся загруженные файлы
AUTH_USER_MODEL | какая модель используется для пользователей. Задаётся до первой миграции
[/TABLE]
[Normal] 6. Своя модель пользователя. accounts/models.py:
[TABLE]
from django.contrib.auth.models import AbstractUser /  /  / class User(AbstractUser): /     """Пользователь магазина. Пока ничем не отличается от стандартного."""
[/TABLE]
[Normal] accounts/admin.py — регистрируем её со стандартным оформлением раздела пользователей:
[TABLE]
from django.contrib import admin / from django.contrib.auth.admin import UserAdmin /  / from .models import User /  / admin.site.register(User, UserAdmin)
[/TABLE]
[Normal] 7. config/urls.py — разрешаем runserver отдавать загруженные файлы. Только в режиме разработки (DEBUG = True), в продакшене этим займётся веб-сервер:
[TABLE]
from django.conf import settings / from django.conf.urls.static import static / from django.contrib import admin / from django.urls import path /  / urlpatterns = [ /     path("admin/", admin.site.urls), / ] /  / if settings.DEBUG: /     urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
[/TABLE]
[Normal] 8. Создать миграции, базу и суперпользователя:
[TABLE]
python manage.py makemigrations accounts / python manage.py migrate / python manage.py createsuperuser
[/TABLE]
[Normal] Порядок важен: сначала миграция accounts, потом migrate. Если запустить migrate раньше, Django создаст таблицы для стандартного пользователя, и дальше будет ошибка InconsistentMigrationHistory (как в лабораторной №3). Решение на этом этапе простое: удалить db.sqlite3 и повторить.
[Normal] 9. Создать .gitignore и первый коммит:
[TABLE]
venv/ / __pycache__/ / *.pyc / db.sqlite3 / media/
[/TABLE]
[TABLE]
git init / git add . / git commit -m "Проект магазина: настройки и своя модель пользователя"
[/TABLE]
[Heading 1] Часть 3. Практика — модели каталога (≈25 мин)
[Normal] Что делаем и зачем: описываем две главные сущности витрины: категорию и товар.
[Normal] 1. catalog/models.py:
[TABLE]

[TABLE]
Элемент | Что означает
SlugField | короткое имя латиницей для адреса страницы: /category/laptops/ вместо /category/3/. Такие адреса понятны людям и поисковикам
DecimalField(max_digits=10, decimal_places=2) | точное десятичное число. Деньги никогда не хранят во FloatField: 0.1 + 0.2 во float равно 0.30000000000000004, и копейки начнут теряться
PositiveIntegerField | целое число не меньше нуля: остаток не может быть отрицательным
ImageField(upload_to="products/") | путь к картинке; сам файл лежит в MEDIA_ROOT/products/. Требует Pillow
is_active | «мягкое» скрытие товара: снять с продажи, не удаляя. Удалить товар, который уже есть в заказах, будет нельзя (см. лабораторную №0.3)
validators=[MinValueValidator(...)] | проверка в формах и admin panel: пользователь увидит понятную ошибку
CheckConstraint | то же правило на уровне базы данных: его не обойти даже кодом, который пишет в БД в обход форм
search_index и save() | служебное поле для поиска, editable=False скрывает его из форм. Зачем оно, разберём в части 7
@property in_stock | вычисляемое свойство: в шаблоне пишется {{ product.in_stock }} без скобок
[/TABLE]
[Normal] В Django 6 параметр ограничения называется condition=. В старых версиях и примерах из интернета встречается check= — он удалён.
[Normal] 2. catalog/admin.py:
[TABLE]

[Normal] prepopulated_fields заполняет slug прямо в браузере, пока вы набираете название. Кириллицу admin panel переводит в латиницу сама: «Мониторы» → monitory. list_editable позволяет менять цену и остаток прямо в списке товаров, не открывая каждую карточку.

[Heading 1] Часть 4. Практика — команда заполнения каталога (≈15 мин)

[Heading 1] Часть 7. Практика — поиск, сортировка, постраничный вывод (≈25 мин)
[Normal] Что делаем и зачем: покупатель ищет товар по названию, выбирает порядок сортировки и листает каталог по 8 товаров на странице. Все три параметра передаются в адресе и должны сочетаться между собой: /category/storage/?q=ssd&sort=cheap&page=2.
[Normal] 1. Почему поиск через search_index. В лабораторной №0.1 мы видели: на SQLite icontains не учитывает регистр только для латиницы. Запрос «монитор» не найдёт «Монитор». Для магазина это неприемлемо, а итоговые проекты вы будете сдавать на SQLite. Решение, которое работает на любой СУБД: при каждом сохранении товара метод save() записывает в служебное поле search_index название и описание в нижнем регистре, а при поиске в нижний регистр переводится и запрос. Python, в отличие от SQLite, переводит в нижний регистр и кириллицу.
[Normal] Ограничение подхода: массовые операции Product.objects.update(...) и bulk_create метод save() не вызывают, и search_index для таких записей не обновится. В PostgreSQL для поиска есть более мощные средства (полнотекстовый поиск django.contrib.postgres.search), но это тема следующих блоков.

Элемент | Что означает
SORT_OPTIONS | белый список сортировок. Значение из адреса не передаётся в order_by напрямую: иначе пользователь мог бы отсортировать по любому полю, включая служебные, или вызвать ошибку 500 несуществующим полем
