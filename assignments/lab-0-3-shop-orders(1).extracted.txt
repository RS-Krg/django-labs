[Title] Лабораторная работа №0.3: Интернет-магазин на Django — корзина, заказы, личный кабинет. Итоговое задание
[Normal] Продолжительность: ~3,5–4 часа (2 семинара; что не успели на занятии, доделывается дома) + итоговое самостоятельное задание (часть 11)
[Normal] Цель: превратить витрину из лабораторной №0.2 в работающий магазин. Покупатель кладёт товары в корзину, регистрируется, оформляет заказ, и остатки на складе списываются в одной транзакции. В конце лабораторной — итоговое самостоятельное задание: свой магазин по варианту.
[Normal] Что понадобится: проект shop в состоянии конца лабораторной №0.2: приложения accounts (своя модель пользователя) и catalog, заполненный командой seed_catalog каталог, общий templates/base.html, 6 проходящих тестов.
[Normal] Все команды выполняются в папке проекта при активированном окружении. Каждую часть советуем завершать коммитом.
[Heading 1] Часть 1. Теория (≈15 мин)
[Heading 2] 1.1 Сессии: где живёт корзина
[Normal] HTTP не помнит предыдущих запросов: каждый запрос браузера для сервера новый. Чтобы узнать посетителя, Django использует сессию:
[Normal] 1. При первой записи в сессию Django создаёт запись в таблице django_session со случайным ключом.
[Normal] 2. Ключ уходит в браузер в cookie sessionid. Сами данные остаются на сервере.
[Normal] 3. При следующих запросах браузер присылает cookie, и Django загружает данные в request.session — объект, похожий на словарь.
[Normal] Вход в систему тоже работает через сессию: после логина в ней хранится номер пользователя. Поэтому корзину удобно держать там же: она есть и у анонимного посетителя, и у вошедшего.
[Normal] Две особенности, о которых нужно помнить:
[List Bullet] данные сессии хранятся в формате JSON, а у JSON ключи словаря — только строки. Поэтому корзина хранится как {"7": 2}, а не {7: 2};
[List Bullet] Django сохраняет сессию, только если заметил изменение. Присваивание request.session["cart"] = ... он видит, а изменение внутри вложенного словаря — нет. В таких случаях ставят request.session.modified = True.
[Heading 2] 1.2 Транзакции: всё или ничего
[Normal] Оформление заказа — это несколько записей в базу: сам заказ, по строке на каждый товар, уменьшение остатка каждого товара. Если на третьем товаре выяснится, что его не хватает, первые две записи уже сделаны. Получится заказ без части товаров, а остатки уменьшены неправильно.
[Normal] Транзакция объединяет несколько операций в одну: либо выполняются все, либо ни одна. В Django это декоратор или блок transaction.atomic: если внутри возникло исключение, все изменения откатываются.
[Normal] Вторая проблема — гонка. Два покупателя одновременно покупают последний товар: оба прочитали «остаток 1», оба оформили, остаток стал −1. Средства защиты:
[TABLE]
Средство | Что делает
select_for_update() | блокирует прочитанные строки до конца транзакции: второй покупатель ждёт, пока первый закончит. В PostgreSQL блокируются строки, SQLite такого не умеет (Django просто игнорирует вызов), но SQLite и так допускает только одну пишущую транзакцию одновременно
F("stock") - n | уменьшение остатка внутри базы данных одной командой UPDATE ... SET stock = stock - n, а не «прочитать в Python, вычесть, записать»
PositiveIntegerField | база не даст сохранить отрицательный остаток
[/TABLE]
[Heading 2] 1.3 Цена на момент заказа
[Normal] Цены меняются. Если в позиции заказа хранить только ссылку на товар, то после подорожания старые заказы «подорожают» задним числом, а бухгалтерия не сойдётся. Поэтому в позиции заказа копируют цену на момент покупки. Это общий принцип для документов в корпоративных системах: документ фиксирует состояние на дату создания.
[Heading 2] 1.4 Где писать бизнес-логику
[Normal] Оформление заказа нужно не только странице checkout. Позже его будут вызывать REST API, мобильное приложение, импорт заказов из маркетплейса. Если логика написана внутри view, её придётся копировать. Поэтому операции с несколькими моделями выносят в отдельный модуль services.py: обычные функции, которые принимают данные и выполняют операцию. View остаётся тонким: разбирает запрос, вызывает сервис, показывает результат.

[Normal] 2. Класс корзины cart/cart.py. Он прячет детали хранения в сессии от остального кода:
[TABLE]
from dataclasses import dataclass / from decimal import Decimal /  / from catalog.models import Product /  / CART_SESSION_KEY = "cart" /  /  / @dataclass / class CartLine: /     product: Product /     quantity: int /  /     @property /     def total(self): /         return self.product.price * self.quantity /  /  / class Cart: /     """Корзина покупателя. Хранится в сессии в виде {"id товара": количество}.""" /  /     def __init__(self, request): /         self.session = request.session /         self.items = self.session.get(CART_SESSION_KEY, {}) /  /     def get_quantity(self, product): /         return self.items.get(str(product.pk), 0) /  /     def add(self, product, quantity=1, replace=False): /         """Добавляет товар, но не больше остатка. Возвращает итоговое количество.""" /         key = str(product.pk) /         if not replace: /             quantity += self.get_quantity(product) /         quantity = min(quantity, product.stock) /         if quantity > 0: /             self.items[key] = quantity /         else: /             self.items.pop(key, None) /         self.save() /         return quantity /  /     def remove(self, product): /         self.items.pop(str(product.pk), None) /         self.save() /  /     def clear(self): /         self.items = {} /         self.save() /  /     def save(self): /         self.session[CART_SESSION_KEY] = self.items /         self.session.modified = True /  /     def lines(self): /         products = Product.objects.filter(pk__in=self.items.keys(), is_active=True) /         return [CartLine(product, self.items[str(product.pk)]) for product in products] /  /     def total_price(self): /         return sum((line.total for line in self.lines()), Decimal("0")) /  /     def __len__(self): /         return sum(self.items.values())
[/TABLE]
[TABLE]
Элемент | Что означает
@dataclass CartLine | маленький класс «строка корзины»: товар, количество и сумма. @dataclass сам пишет __init__ по аннотациям полей
self.session.get(...) | читаем корзину, не создавая её. Если бы мы сразу записывали пустую корзину в сессию, Django заводил бы сессию и ставил cookie каждому посетителю каталога
str(product.pk) | ключи — строки, см. п. 1.1
min(quantity, product.stock) | в корзину нельзя положить больше, чем есть на складе
lines() | один SQL-запрос за всеми товарами корзины (pk__in). Снятые с продажи товары в корзину не попадают
__len__ | len(cart) — общее количество штук, для значка в шапке
[/TABLE]

[Normal] 4. View корзины cart/views.py:
[TABLE]
from django.contrib import messages / from django.shortcuts import get_object_or_404, redirect, render / from django.views.decorators.http import require_POST /  / from catalog.models import Product /  / from .cart import Cart / from .forms import CartAddForm /  /  / @require_POST / def cart_add(request, product_id): /     product = get_object_or_404(Product, pk=product_id, is_active=True) /     form = CartAddForm(request.POST) /     if not form.is_valid(): /         messages.error(request, "Укажите количество от 1 до 99.") /         return redirect(product) /  /     cart = Cart(request) /     quantity = form.cleaned_data["quantity"] /     replace = form.cleaned_data["replace"] /     requested = quantity if replace else cart.get_quantity(product) + quantity /     in_cart = cart.add(product, quantity, replace=replace) /  /     if in_cart == 0: /         messages.error(request, f"Товара «{product.name}» нет в наличии.") /     elif in_cart < requested: /         messages.warning( /             request, f"На складе только {product.stock} шт. товара «{product.name}»." /         ) /     else: /         messages.success(request, f"«{product.name}»: в корзине {in_cart} шт.") /     return redirect("cart:detail") /  /  / @require_POST / def cart_remove(request, product_id): /     product = get_object_or_404(Product, pk=product_id) /     Cart(request).remove(product) /     messages.info(request, f"«{product.name}» удалён из корзины.") /     return redirect("cart:detail") /  /  / def cart_detail(request): /     cart = Cart(request) /     lines = cart.lines() /     context = { /         "lines": lines, /         "total": sum(line.total for line in lines), /     } /     return render(request, "cart/detail.html", context)

[List Bullet] положить товары в корзину до регистрации, потом зарегистрироваться или войти: корзина сохранилась. При входе Django меняет ключ сессии (защита от подмены сессии), но данные переносит в новую;
[List Bullet] выйти: корзина очистилась. При выходе Django полностью удаляет сессию, чтобы следующий человек за тем же компьютером не увидел чужих данных.

Решение | Почему так
user — on_delete=PROTECT | заказы — учётные документы. Нельзя «случайно» потерять историю продаж, удалив покупателя
OrderItem.order — CASCADE | строки не существуют без своего заказа: удалили заказ — удалились и строки
OrderItem.product — PROTECT | товар, который кто-то купил, удалить нельзя, только скрыть (is_active). Вот зачем в лабораторной №0.2 появилось это поле
OrderItem.price | цена копируется в момент заказа, см. п. 1.3
full_name, phone, address в заказе, а не в пользователе | получатель конкретного заказа может отличаться от владельца учётной записи
total_price — свойство, а не поле | сумма всегда считается по строкам и не может «разойтись» с ними
[/TABLE]

from django.db import transaction / from django.db.models import F /  / from catalog.models import Product /  / from .models import Order, OrderItem /  /  / class OutOfStockError(Exception): /     """Товара на складе меньше, чем в корзине.""" /  /  / @transaction.atomic / def place_order(user, order_form, cart_lines): /     """Создаёт заказ из строк корзины и списывает товар со склада. /  /     Всё выполняется в одной транзакции: если какого-то товара не хватает, /     не сохранится ни заказ, ни его позиции, ни изменения остатков. /     """ /     product_ids = [line.product.pk for line in cart_lines] /     products = Product.objects.select_for_update().in_bulk(product_ids) /  /     order = order_form.save(commit=False) /     order.user = user /     order.save() /  /     for line in cart_lines: /         product = products[line.product.pk] /         if product.stock < line.quantity: /             raise OutOfStockError( /                 f"Товара «{product.name}» на складе {product.stock} шт., " /                 f"а в корзине {line.quantity}." /             ) /         OrderItem.objects.create( /             order=order, product=product, price=product.price, quantity=line.quantity /         ) /         Product.objects.filter(pk=product.pk).update(stock=F("stock") - line.quantity) /  /     return order /  /  / @transaction.atomic / def cancel_order(order): /     """Отменяет заказ и возвращает товары на склад.""" /     for item in order.items.all(): /         Product.objects.filter(pk=item.product_id).update(stock=F("stock") + item.quantity) /     order.status = Order.Status.CANCELLED /     order.save(update_fields=["status", "updated_at"])
[/TABLE]
[TABLE]
Элемент | Что означает
@transaction.atomic | вся функция — одна транзакция. Исключение OutOfStockError отменит уже созданный заказ и строки
select_for_update().in_bulk(ids) | заново читаем товары из базы (остаток мог измениться, пока покупатель заполнял форму) с блокировкой строк. in_bulk возвращает словарь {id: товар}
price=product.price | снимок цены
update(stock=F("stock") - n) | атомарное уменьшение остатка в самой базе
class OutOfStockError(Exception) | своё исключение: view поймает именно его и покажет понятное сообщение, а не страницу ошибки 500
save(update_fields=[...]) | записать только указанные поля, а не всю строку
[/TABLE]
[Normal] Проверку остатка можно было бы сделать до создания заказа. Здесь она намеренно стоит внутри цикла после записи, чтобы на практике увидеть откат транзакции (часть 8).

Элемент | Что означает
request.user.orders | обратная связь related_name="orders": только заказы текущего пользователя. Чужой заказ по номеру даст 404, как в лабораторной №0.1
prefetch_related("items") | строки всех заказов списка загружаются одним дополнительным запросом, а не отдельным запросом на каждый заказ. select_related работает для связей «к одному» (через JOIN), prefetch_related — для связей «ко многим»
"items__product" | заодно подгрузить товары строк: в шаблоне выводится item.product.name
cart.clear() после place_order | корзина очищается, только если заказ действительно сохранён

Элемент | Что означает
TabularInline | строки заказа выводятся таблицей внутри страницы заказа
readonly_fields, can_delete, has_add_permission | строки заказа нельзя менять, удалять и добавлять: заказ — документ
"status" в readonly_fields | статус нельзя выставить вручную в карточке: иначе менеджер мог бы поставить «Отменён», не вернув товар на склад. Статус меняется только действиями
actions | действия над выбранными в списке заказами (выпадающий список над таблицей)
queryset.filter(status=from_status) | действие меняет только заказы в подходящем статусе: выполнить заказ, минуя доставку, нельзя
cancel вызывает cancel_order | та же функция, что и у покупателя: правило «отмена возвращает товар» записано в одном месте
get_queryset с prefetch_related | список заказов с суммами строится за 2 запроса, а не за 1 + N
[/TABLE]

[Heading 1] Часть 11. Итоговое самостоятельное задание
[Heading 2] 11.1 Что нужно сделать
[Normal] Каждый студент самостоятельно разрабатывает свой интернет-магазин (или сервис с покупкой и бронированием) по варианту — полноценное веб-приложение на Django с собственным фронтендом на шаблонах, которое запускается на локальной машине на SQLite. Код лабораторных №0.2 и №0.3 можно и нужно брать за основу: задача — перенести и развить решения для своей предметной области.
[Normal] Вариант складывается из двух частей:
[List Bullet] предметная область (домен) — что продаёт магазин и какое у него особое бизнес-правило. Определяется по первой букве фамилии;
[List Bullet] модуль — дополнительная подсистема. Определяется по первой букве имени.
[Normal] Шифр варианта записывается как Д<номер домена>-М<номер модуля>, например Д2-М1.
[Heading 2] 11.2 Как определить свой вариант
[Normal] Буквы берутся из написания фамилии и имени в списке группы (журнале). Буква «Ё» считается как «Е», «Й» — как «И».
[Normal] Домен — по первой букве фамилии:

[/TABLE]
[Normal] Модуль — по первой букве имени:
[TABLE]

[Normal] Группы букв подобраны так, чтобы домены и модули распределялись по студентам примерно поровну: на частые буквы (К, С, П, М) приходится по одному домену, на редкие — по несколько.
[Normal] Примеры: Смирнова Анна → Д2-М1 (спорттовары, отзывы). Иванов Пётр → Д8-М4 (прокат, отчёты). Ким Дмитрий → Д1-М2 (книги, промокоды).
[Normal] Если варианты совпали. Внутри одной академической группы шифры не должны повторяться. Порядок разрешения совпадений:
[Normal] 1. Студенты группы выписываются в порядке списка группы (по алфавиту фамилий), у каждого вычисляется шифр.
[Normal] 2. Шифр сохраняет тот, кто стоит в списке раньше.
[Normal] 3. Следующему с таким же шифром номер модуля увеличивается на 1 по кругу (М4 → М1), пока шифр не станет свободным.
[Normal] 4. Если в домене заняты все четыре модуля, берётся следующий домен (Д12 → Д1) с исходным модулем, и проверка повторяется.
[Normal] Пример: в группе Иванов Пётр и Ильин Сергей. У обоих Д8-М4. Иванов раньше по алфавиту, он сохраняет Д8-М4. Ильину модуль сдвигается: Д8-М1, если этот шифр свободен.
[Normal] Староста группы до первой контрольной точки составляет таблицу «ФИО — буквы — шифр» и присылает преподавателю, преподаватель утверждает. После утверждения вариант не меняется. В разных академических группах варианты могут совпадать, но работы сравниваются между собой (п. 11.7).
[Normal] Своя тема. Вместо домена по варианту можно предложить свою предметную область: например, ту, с которой вы работаете или собираетесь работать. Условия:
[List Bullet] тема согласуется с преподавателем до первой контрольной точки, после этого меняется только домен, модуль остаётся по имени;
[List Bullet] в теме есть товары или услуги, корзина или бронирование, заказ с позициями и учётом остатков (мест, экземпляров, слотов), и предложено собственное бизнес-правило не проще, чем у доменов из таблицы;
[List Bullet] нельзя: магазин компьютерной техники из лабораторных, блог, список задач, любая тема без оформления заказа;
[List Bullet] тема не должна совпадать с темой другого студента группы.

[Heading 2] 11.4 Домены
[Normal] Для каждого домена указаны обязательные сущности (сверх категорий, заказов и позиций заказа), атрибут для фильтра каталога и бизнес-правило, которое должно быть реализовано и покрыто тестом.
[Normal] Д1. Книжный магазин. Сущности: книга, автор (у книги может быть несколько авторов — ManyToManyField), издательство, жанр. Фильтры: автор, год издания. Правило: у книги есть возрастная маркировка (0+, 6+, 12+, 16+, 18+); в модели пользователя есть дата рождения. Книги 18+ нельзя оформить в заказ, если у покупателя не указана дата рождения или ему меньше 18 лет: при оформлении — понятное сообщение, заказ не создаётся.
[Normal] Д2. Спортивные товары. Сущности: товар, бренд, вариант товара (размер и остаток для каждого размера). Фильтры: бренд, наличие нужного размера. Правило: в корзину кладётся конкретный размер; остаток хранится и списывается у варианта; товар, у которого ни один размер не в наличии, показывается как «нет в наличии», и его нельзя положить в корзину.
[Normal] Д3. Продукты с доставкой по времени. Сущности: товар (с единицей измерения: шт., кг, л), слот доставки (дата, интервал времени, максимальное число заказов). Фильтры: единица измерения, «только в наличии». Правило: минимальная сумма заказа 1000 ₽; при оформлении покупатель выбирает слот на ближайшие 3 дня; заполненные и прошедшие слоты выбрать нельзя; проверка заполненности слота — внутри транзакции оформления.
[Normal] Д4. Мебель. Сущности: товар, материал или цвет (вариант исполнения со своей ценой), зона доставки (название, стоимость). Фильтры: материал, диапазон цены. Правило: стоимость доставки зависит от выбранной зоны; при сумме товаров от 50 000 ₽ доставка бесплатная; опция «сборка» добавляет 10 % к стоимости товаров. Стоимость товаров, доставки и сборки сохраняются в заказе отдельными полями.
[Normal] Д5. Билеты на мероприятия. Сущности: площадка, мероприятие (дата и время), категория мест на мероприятии (название, цена, количество мест). Фильтры: площадка, дата. Правило: прошедшие мероприятия не показываются в афише, и билеты на них купить нельзя (проверка и при оформлении); в одном заказе не больше 6 билетов на одно мероприятие; места списываются по категориям.
[Normal] Д6. Аптека. Сущности: препарат (форма выпуска, признак «рецептурный»), действующее вещество, пункт выдачи (адрес, часы работы). Фильтры: форма выпуска, действующее вещество. Правило: способ получения — доставка или самовывоз из пункта выдачи; если в корзине есть рецептурный препарат, доставка недоступна (только самовывоз), а покупатель предупреждается об этом ещё в корзине.
[Normal] Д7. Цветы и подарки. Сущности: товар (букет, подарок), повод (день рождения, 8 марта и т.п.; у товара может быть несколько поводов — ManyToManyField), открытка. Фильтры: повод, ценовой диапазон. Правило: дата и время доставки — не раньше чем через 3 часа от момента оформления и не позже чем через 30 дней, только с 9:00 до 21:00; текст открытки до 200 символов. Все проверки — в форме оформления с понятными ошибками.
[Normal] Д8. Прокат инструмента. Сущности: модель инструмента (цена за сутки, залог), экземпляр (инвентарный номер, состояние), бронь (экземпляр, дата начала, дата окончания). Фильтры: категория, «свободен на даты». Правило: покупатель выбирает даты; нельзя забронировать экземпляр на период, пересекающийся с существующей бронью (проверка пересечения — запросом к базе внутри транзакции); стоимость = цена за сутки × число суток + залог.
[Normal] Д9. Онлайн-школа. Сущности: курс, преподаватель, поток (дата старта, лимит мест), урок (материалы курса). Фильтры: преподаватель, дата старта. Правило: запись на поток с ограничением мест; нельзя купить один и тот же курс повторно, пока предыдущая запись не отменена; материалы уроков видны только тем, чей заказ менеджер перевёл в статус «Оплачен» (такой статус нужно добавить в модель заказа).
[Normal] Д10. Доставка еды из кафе. Сущности: блюдо, раздел меню, добавка (своя цена; у блюда — набор доступных добавок через ManyToManyField). Фильтры: раздел, «вегетарианское», «острое». Правило: заказы принимаются только с 10:00 до 22:00 по времени сервера; минимальная сумма 700 ₽; одно и то же блюдо с разным набором добавок — разные позиции корзины и заказа, цена позиции учитывает добавки.
[Normal] Д11. Автозапчасти. Сущности: запчасть, производитель, марка и модель автомобиля (годы выпуска), совместимость запчасти с моделями (ManyToManyField). Фильтры: марка → модель → год. Правило: у покупателя есть «гараж» — сохранённые автомобили, по которым каталог фильтруется в один клик; при оформлении заказа покупатель получает предупреждение, если запчасть не совместима ни с одним автомобилем из его гаража.
[Normal] Д12. Маркетплейс мастеров. Сущности: мастер (профиль, связанный с пользователем), изделие (принадлежит мастеру), заказ с позициями от разных мастеров, у каждой позиции свой статус. Фильтры: мастер, материал. Правило: мастера (группа «Мастера») работают на сайте, а не в admin panel: видят и редактируют только свои изделия, видят только позиции заказов со своими изделиями и меняют статус только этих позиций. Чужое изделие или чужая позиция — 404.
[Heading 2] 11.5 Модули
[Normal] М1. Отзывы и рейтинг.
[List Bullet] Модель отзыва: товар, автор, оценка от 1 до 5, текст, дата, признак «одобрен».
[List Bullet] Оставить отзыв может только покупатель, у которого есть выполненный заказ с этим товаром; один отзыв на товар от одного покупателя (UniqueConstraint).
[List Bullet] Отзыв появляется на сайте после одобрения менеджером (действие в admin panel).
[List Bullet] В каталоге и на странице товара — средняя оценка и число отзывов, посчитанные в базе (annotate с Avg и Count), сортировка «по рейтингу».
[Normal] М2. Промокоды и скидки.
[List Bullet] Модель промокода: код, тип скидки (процент или фиксированная сумма), размер, период действия, лимит использований, минимальная сумма заказа, признак активности.
[List Bullet] Промокод вводится в корзине и хранится в сессии; каждое невыполненное условие — своё понятное сообщение (истёк, исчерпан, сумма меньше минимальной и т.д.).
[List Bullet] Скидка не может быть больше суммы заказа; код и сумма скидки сохраняются в заказе.
[List Bullet] Счётчик использований увеличивается в той же транзакции, что и оформление заказа (F()); промокод с исчерпанным лимитом не применяется, даже если его успели положить в корзину.
[Normal] М3. Избранное и уведомления о поступлении.
[List Bullet] Избранное: добавить и убрать товар (POST), страница «Избранное», отметка на карточках каталога; пара «пользователь — товар» уникальна.
[List Bullet] Модель уведомления: пользователь, текст, ссылка, дата, признак «прочитано».
[List Bullet] Когда остаток товара меняется с 0 на положительный (менеджер пополнил склад в admin panel), всем, у кого товар в избранном, создаётся уведомление «Товар снова в наличии».
[List Bullet] Счётчик непрочитанных уведомлений в шапке, страница уведомлений, отметка «прочитано».
[Normal] М4. Отчёты для менеджера.
[List Bullet] Страница /reports/ доступна только группе «Менеджеры» и администратору; остальным — 403.
[List Bullet] Выбор периода (с — по, по умолчанию последние 30 дней) через форму с проверкой дат.
[List Bullet] Выручка по дням без учёта отменённых заказов, число заказов по статусам, топ-10 товаров по выручке.
[List Bullet] Все расчёты — агрегатами в базе данных (annotate, aggregate, Sum, Count, TruncDate), а не циклами в Python; выгрузка отчёта в CSV.

[Heading 2] 11.7 Как проходит приёмка
[Normal] Защита занимает около 15 минут и идёт по одному протоколу для всех.
[Normal] 1. Развёртывание с нуля по README. Преподаватель (или студент на компьютере в аудитории) клонирует репозиторий в пустую папку и выполняет только команды из README: создание окружения, pip install -r requirements.txt, migrate, seed_demo, runserver. Если проект не запускается за 10 минут по инструкции, защита переносится.
[Normal] 2. Автоматические проверки: python manage.py check, python manage.py makemigrations --check (нет забытых миграций), python manage.py test (все тесты проходят). Если тесты не проходят, защита переносится.
[Normal] 3. Сценарий покупателя: регистрация, поиск и фильтры, корзина, оформление, личный кабинет, отмена.
[Normal] 4. Сценарий менеджера: вход демонстрационным менеджером, обработка заказа действиями, проверка, что лишних разделов нет.
[Normal] 5. Негативные проверки: чужой заказ по прямой ссылке, оформление без входа, количество больше остатка, нарушение бизнес-правила домена, недопустимое применение модуля (например, просроченный промокод). Ожидается понятное сообщение или 403/404, но не ошибка 500.
[Normal] 6. Вопросы по коду. Преподаватель открывает 2–3 места в коде и просит объяснить, что там происходит и почему сделано так.
[Normal] 7. Доработка на месте (до 10 минут): небольшое изменение по заданию преподавателя. Например, добавить поле в модель и вывести его на странице, добавить вариант сортировки, изменить порог в бизнес-правиле и поправить тест.
[Normal] Правила:
[List Bullet] код лабораторных можно использовать как основу, это ожидается;
[List Bullet] пользоваться документацией, примерами и ИИ-ассистентами можно, но студент отвечает за каждую строку проекта. Если студент не может объяснить фрагмент своего кода, баллы за соответствующий критерий не засчитываются;
[List Bullet] история Git должна отражать работу: не меньше 15 коммитов, распределённых по контрольным точкам. Один большой коммит в конце — 0 баллов за критерий «Git и качество кода» и дополнительные вопросы на защите;
[List Bullet] если в работах разных студентов найден совпадающий код (кроме кода лабораторных), обе работы защищаются повторно с расширенной доработкой на месте.
